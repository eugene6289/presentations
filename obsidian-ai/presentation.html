Section 01 · Architecture

我如何設計這個架構

核心決定只有一個：不做語意搜尋。知識就是一堆結構良好、彼此連結的 Markdown，AI 靠「讀索引 + 順連結」導航，而不是丟進向量庫做相似度比對。這個決定牽動了整套結構。

💡 為什麼不用向量庫

向量庫把知識變成「不透明的一團 embedding」——查得到但看不懂、無法版控、無法人工校對。改用純 Markdown + wikilink，知識對人和對 AI 都是可讀、可 diff、可 review 的一等公民；找答案靠明確的三層索引，結果可追溯、可解釋。

三層導航（Three-layer navigation）

找東西不盲目 grep 全 vault，而是從主索引一路收斂：先挑領域、再挑專案、再順連結追到頁面。

L1
主索引 wiki/index.md
Master Index — 領域入口表 + 跨領域 tag 表。查資料的起點。
L2
領域總覽 00 XX總覽 (Start Here)
work / research 各一個 MOC，挑對的專案或主題。
L3
專案／主題總覽 00 總覽 (Start Here)
每個專案自己的 MOC：目錄表 + 依角色的閱讀路徑。
L4
具體頁面 · 順著 wikilink 追
跨領域抓同類型（所有 meeting、某人相關…）改用 tag 面板。

結構軸：領域為綱，類型走 tag

🗂 資料夾＝領域（唯一結構軸）

頂層只用「領域」分：work/（專案文件、決策 ADR、會議、流程 playbook）與 research/（純知識探索）。這是唯一的資料夾切分方式。

🏷 類型走 tag，跨領域

meeting / decision / person / playbook… 用 tag 橫跨所有領域，不用資料夾硬切。Obsidian tag 面板一點就列出同類型。

🔗 wikilink 建關係

內部連結一律 [[頁面標題]]；跨資料夾或同名檔用 [[資料夾/檔名｜顯示名]]。app.json 設 newLinkFormat: absolute，新連結自動帶絕對路徑消歧。

頁面成熟度：status 是單一真相來源

每頁 frontmatter 的 status: 標「這頁可信到什麼程度」，並配對應的頁首 banner，避免把規劃中的東西誤當現況。

status意義頁首 banner
current現況 / 已實作（預設）無
spec規格 / 規劃中，非成品> [!warning] 規格文件（規劃中），非現況
draft草稿，未核實> [!note] 草稿，內容尚未核實
deprecated已棄用，僅供歷史參考> [!danger] 已棄用
ℹ️ 撰寫慣例（讓 graph 與導航長得起來）

檔名 NN 中文標題.md（數字前綴定資料夾內閱讀順序）· 每個資料夾一個 00 總覽 (Start Here) MOC · 重點用 callout（[!info]/[!warning]/[!tip]…）· 每個專案一份 <專案> 詞彙表。

Section 02 · Version Control

如何版控

vault 是分享給同事的 git 私有 repo，每人各自 clone、用自己的 Obsidian 開。刻意不開 Obsidian Sync——兩套同步同時寫同一批檔會打架。

⚠️ 走 git，不是 Obsidian Sync

Obsidian Sync 與 git 同時同步同一個 vault 會互相覆蓋、產生衝突殘檔。全隊統一走 git：好處是純文字 Markdown 天生適合版控——diff 清楚、衝突好解、歷史可追。

🔄 日常流程

1git pull編輯前先拉同事最新內容
→
2小步 commit常 commit、訊息清楚
→
3git push改完盡早推上去
🧩 衝突怎麼辦

都是純文字 Markdown，手動解很直覺——沒有二進位打架的問題。

🚫 為什麼把原始檔擋在 repo 外

raw/（原始來源投放區：Excel、PDF、逐字稿）是本機自用，在 .gitignore 內、只保留 README。原因：避免二進位撐肥 git 歷史，且原始檔通常較敏感。真正的知識全在消化後的 wiki/。

🔐 敏感資訊政策

同事全可信、內容全分享，但敏感點（密鑰、正式機位址、弱點）用 > [!danger] 敏感：… 標顯眼，且不把可用的密鑰明文留在頁面。

關鍵在 .gitignore：per-user 狀態不進、共享設定要進

Obsidian 的 .obsidian/ 混了「個人 UI 狀態」和「團隊共享設定」，要精準切開才不會互相覆蓋。

是否進 repo檔案原因
忽略workspace.json每個人的面板佈局，屬 per-user UI 狀態
忽略plugins/*/data.json · sync.json各 plugin 的本機設定
忽略.DS_StoremacOS 殘檔
共享app.json已設 newLinkFormat: absolute，連結格式全隊一致
共享graph.json · core/community-plugins.jsongraph 樣式與啟用的 plugin 清單
共享plugins/terminal/*內含的 community plugin，新同事首開需手動信任
Section 03 · Spec Ingestion

把規格書轉成知識庫：Excel → PDF → Markdown

企劃組的規格常是線上 Excel。它進不了向量庫也不好連結，我把它變成一條固定 pipeline，落地成帶 status: spec 的結構化 Markdown 頁，並登錄回母專案。

來源線上 Excel企劃維護的規格表.xlsx
→
匯出PDF凍結成一份可讀快照.pdf
→
投放raw/丟進本機暫存區（不進 repo）.gitignore
→
消化spec-ingest套規格頁模板skill
→
產出md 規格頁status: spec + warning banner + 八段式wiki/
→
登錄母專案更新 MOC、寫 logMOC
📐 規格頁模板（spec-ingest 封裝的三件事）

① frontmatter status: spec　② 頁首 > [!warning] banner（標「規劃中、非現況」）　③ 00 八段式結構 + 「登錄回母專案」四件套清單。讓 AI 產出的規格頁結構一致、不會被誤讀成已實作。

真實案例：opTool「批次上傳道具」規格

📄 來源

raw/規格書-道具批量上傳.pdf（4 頁，「+批次新增道具」功能規格）。

🧩 拆成多頁

  • 00 批次上傳道具總覽（MOC）
  • 01 操作流程與彈窗
  • 02 錯誤處理與略過邏輯
  • 03 欄位對應規則

🏆 04 範例＝黃金樣本

04 範例-限時組裝足球拉霸人：四階合成樹 + 30 筆道具清單 + 對應批次模板的欄位固定值，可當實作／QA 的黃金樣本。此頁 current，但工具本身仍 spec（頁內已標區隔）。

ℹ️ 一份來源常產生數個頁面

ingest 不是「一份 PDF 換一頁」，而是把內容拆成有意義的多個 wiki 頁、各設好 frontmatter、頁面之間用 wikilink 建立關係，最後更新領域總覽並在 log.md 記一筆。

Section 04 · Using specs in development

如何在專案開發中使用知識庫的規格書

規格頁不是寫完就擺著。它在開發時是「要做成什麼」的單一依據，在測試時是驗收樣本，也記錄了文件與實際程式碼之間的落差。

🎯 規格頁＝實作依據

spec 頁描述的是「要做成什麼」，不是「現在是什麼」。頁首 warning banner 讓開發者一眼分清規劃 vs 現況，不會照著還沒實作的東西誤判現有行為。

🧪 黃金樣本＝QA 驗收

04 範例 把合成樹、30 筆道具、批次模板欄位固定值全列清楚——實作時照著填、QA 時照著驗，是可客觀比對的驗收樣本。

🔍 刻意記錄「文件 vs 程式碼」落差

vault 常用來記錄 vault 之外的真實 repo（如 opTool、Rhino）。這類頁刻意保留 README／文件 與 活的原始碼之間的不一致（容器名不符、設定過時），是「已知問題與陷阱」頁的標準配備。

⚠️ 更新時重新對照活的原始碼

原始碼在 vault 之外、要去真實路徑讀，別假設它在 vault 裡。維護這類文件時重新對照當前程式碼、更新 updated: 日期，別只信舊筆記；也不要默默把「已知問題與陷阱」蒐集的不一致主張「修掉」——那些落差本身就是要保留的知識。

典型迴圈：規格 → 開發 → 回填知識

讀規格頁從專案 MOC 順 wikilink 找到 spec 頁，對齊「要做什麼」
→
照樣本開發以黃金樣本為實作/QA 依據
→
回填現況實作後把 status 由 spec 收斂到 current，更新落差頁與 log
Section 05 · Operation Log

操作紀錄：每次消化都留下軌跡

每一次 ingest（消化來源）、lint（健檢）或大改動，都在 wiki/log.md 記一筆、最新的放最上面。這是 vault 的稽核軌跡——知道每頁怎麼來的、架構為何演進。點開任一筆看細節。

💡 log 為什麼重要

知識庫最怕「不知道某頁是怎麼來的、可不可信」。log 把每次消化的來源、分診判斷、產出、登錄都留下，讓知識可追溯、架構演進有據可查。

Section 06 · Skills

有 skill：團隊怎麼每天使用

使用者不用背流程。丟東西進 raw/、說一句「幫我 ingest」，skill 就會先讀來源、反問確認、再路由。ingest 的兩個 skill 是上下游關係，不是二選一。

投放丟進 raw/文章、逐字稿、規格、會議記錄…
→
總入口raw-ingest分診 · 反問 類型／歸屬／深度／圖片
→
判為規格↳ spec-ingest交棒下游、套規格頁模板
→
落地wiki 頁 + log登錄回母專案、寫一筆 log
raw-ingestspec-ingest
何時用歸屬 / 類型不明（預設從這開始）已確定是企劃規格
角色總入口、分診、路由下游、專門模板
產出現況 / 會議 / 決策 / 研究頁spec 規格頁
關係判為規格 → 交棒 spec-ingest被 raw-ingest 呼叫（或直接用）

🗣 怎麼喚起

  • 不確定 → 「幫我 ingest」（走 raw-ingest 分診）
  • 明確是規格 → 「ingest 這份規格」（直接 spec-ingest）
  • 定期整理 → 「幫我 lint」（找不一致、補缺漏、提連結）

🧹 lint 健檢

掃 wiki/ 找不一致的資料、缺漏（可 web search 補）、值得新增的連結、孤立頁面，提出建議；不確定就回頭問。完成後在 log.md 記一筆。

🤝 團隊 skills 資料夾

vault 另有共享 skills/，每位成員至少貢獻一個：deploy-release（部署發版）、ui-components-pipeline（UI 組件流程）、create-doc（專案分析文件化）。

ℹ️ skill 把「規則」變成「一句話」

ingest 的分診邏輯、規格頁模板、登錄四件套、寫 log——這些規則都封裝進 skill。使用者只要丟檔案 + 一句自然語言，不必記結構；AI 依 skill 走完整流程並保持一致風格。
