P7 · grill-me
標題：動手前：用 /grill-me 追問需求
引言：grill-me 是開發工具裡的一個 skill：動手之前叫它一次，它會先反過來追問。以下是另一個專案的實際紀錄。
圖 1｜輸入　需求原句（grill-prompt.png）
說明：這是全部的輸入。沒有規格、沒有驗收條件、沒有範圍定義——實務上很多需求就是這個樣子。
圖 2｜第一輪　三個問題（grill-round1.png）
說明：追問集中在三件事：這件事真正的觸發點是什麼、改完之後誰維護、有沒有辦法在不上正式環境的情況下驗證。

P8 · grill-me
標題：追問到答得出來為止
圖 1｜第二輪 A　回到原問題（grill-round2a-crop.png）
說明：第一輪的回答沒有回到問題本身，所以再問一次。這一輪出現關鍵發現：需要處理的檔案數，跟原本以為的差很多。
圖 2｜第二輪 B　驗收基準（grill-round2b-crop.png）
說明：接著追問驗收基準：改完之後要拿什麼跟改之前比對。沒有基準，就沒有辦法判斷有沒有改壞。

P9 · grill-me
標題：產出：一份定案的計畫
引言：兩輪之後需求才成案。輸出不是程式，是一份寫進專案的計畫文件。
圖（grill-end.png）圖說：產出的計畫文件（節錄），共 120 行。
右欄三點
原本的需求不成立：一開始要的是「升級 264 個檔案」。追問後確認，真正需要處理的只有 1 個。
結論出現在動手之前：這個判斷不是寫程式寫出來的，是問出來的。寫下去之後才發現，成本是另一回事。
完成標準先定義：改前改後的回應必須逐 byte 相同。先有比對基準，才動第一行。
結語條：這一關的產出不是程式，是一份「接下來照這個做」的共識。

P10 · §09 關卡二 · 寫的時候
標題：人先寫答案，AI 再照著寫
引言：AI 寫得對不對，不靠人逐行看，靠一條事先寫好的檢查來判定。
三步
人先寫下答案：「輸入 Jin Gaming-Coin，應該得到 jin_gaming_coin」——把這句話寫成程式，就是一條檢查。｜規則由人決定
先確認它會失敗：功能還沒寫，這條檢查應該是紅的。若此時仍然通過，代表這條檢查沒有實際作用。｜先紅
AI 照著答案寫實作：實作完成，檢查轉綠。這條規則從此留在檢查集裡，之後每次改動都會自動重驗一次。｜後綠
結語條：順序決定結果：驗收條件由人先定義，AI 的工作是讓實作通過這個條件。產出若與條件不符，在當下就會被判定不通過。

P11 · §10 實際畫面（截圖頁）
標題：紅燈與綠燈
引言：這是關卡二在真實專案裡的樣子，兩張都是實際的執行畫面。
圖 1｜紅燈　功能還沒寫：新寫的 7 條檢查，因為功能還不存在而失敗。先確認它真的抓得到錯，才開始動手寫。
圖 2｜綠燈　功能完成：實作完成後全部通過：這一輪 133 條檢查，0.54 秒跑完，程式格式檢查也一併過關。
結語條：同一套檢查在之後每次改動時都會重新執行，涵蓋範圍不限於本次開發，這是它在維護階段的作用。

P12 · §11 關卡三 · 提交前
標題：提交前：用 /pre-commit-review 掃一遍
引言：另一個 skill：提交之前固定叫一次，把該掃的地方逐項掃過。它檢查的不是功能對不對，是有沒有留下不該留的東西。
四個檢查層級
最高優先 — 密鑰與敏感資料：API 金鑰、密碼、連線字串有沒有被寫進程式；使用者資料有沒有被印到日誌裡。
高 — 資安與功能破壞：注入風險、權限判斷寫漏、這次改動有沒有把既有行為改壞。
中 — 殘留與雜訊：debug 用的印出、臨時測試碼、不該進版控的檔案，有沒有跟著被提交。
中 — 效能與設定：資料庫查詢的寫法、環境設定、型別安全，這些容易在趕工時被略過的地方。
結語條：但它有個先天問題：這是一個「要記得做」的動作。趕的時候最容易略過，而趕的時候最需要它。

P13 · §12 關卡三 · 補強（hook）
標題：用一個 hook，把「要記得做」變成「不做就過不去」
引言：最近加的做法：讓開發工具在偵測到 git commit 的當下自己攔下來，不依賴人記得。
四格
問題 — 紀律會被進度稀釋：做不做，取決於當下記不記得。越忙越容易跳過。｜靠紀律
做法 — 在提交那一刻攔下來：凡是要執行 git commit，先被擋住，並指定去跑審查。｜20 行 shell
流程 — 審完，重跑就過：AI 收到攔截後自己去審、回報發現；處理完重下同一個指令即放行。｜不用改 CI
分寸 — 同一份內容只擋一次：以「這次連線＋這個專案＋這批內容」為單位記錄，不會變成干擾。｜機器強制
程式碼條：攔截 git commit → deny：「這次 commit 還沒做提交前審查，請先呼叫 pre-commit-review」
結語條：不用改 CI、不用每個人記得。目前掛在我自己的環境，之後可直接複製成團隊共用設定。

P14 · §13 關卡四 · 推送前（數字頁）
標題：沒過，程式就送不出去
引言：前面三道靠紀律，這一道是機器強制的：所有檢查重跑一次，全過才放行。
四個數字
189 條自動檢查 — 後端 128 ／ 前端 61
20 個檢查檔案 — 對應各自的功能模組
1 秒內全部跑完 — 後端 0.83 秒、前端 0.16 秒
0 條失敗 — 目前全數通過
底部兩句
任何一條沒過，這份程式就送不進共用版本，自然也不會被部署出去。
涵蓋前端與後端兩個專案。每加一個功能，這個數字就再往上長一點。

P15 · §14 缺口 · 畫面層
標題：四道關卡蓋不到的地方：畫面
引言：189 條檢查驗的是邏輯與資料，不是「按鈕點下去有沒有反應」。這一塊原本只能靠人工點過一遍。
三欄
缺口 — 程式全綠，畫面仍可能是壞的：實際遇過：檢查與建置都通過，但有兩個地方沒被涵蓋到，是靠人開瀏覽器看畫面對不上才發現的。
做法 — 讓 AI 直接操作瀏覽器：Claude in Chrome 可以開真的頁面、點真的按鈕、讀 console 與網路請求。等於把人工要點的那一遍，交給它照著走。
現況 — 試作階段，已實際跑過幾次：目前是先確認它抓得到哪些問題，還沒固定成流程。下一步是挑幾條最常壞的操作路徑，變成每次都跑。
結語條：這一關補的是「還會不會動」。畫面好不好用、順不順，仍然是判斷題，還是由人來看——分工跟前面一樣：人做判斷，機器做重複。

P16 · §15 另一種驗證
標題：沒有新需求的改動，要怎麼驗？
引言：最近幫另一個專案做效能優化，26 個項目。這類改動的驗收條件是「行為完全不變」，先寫檢查那一套用不上，改用另外三段。
三段
第一段 — 先量，再改：動手前先建立基準線，改完量同一個數字。用精確值不用估計值：JS 產物 5,758,513 → 4,827,230 byte。｜−16.2%
第二段 — 逐項列出可能波及誰：每一筆改動都寫成兩欄：可能波及哪些程式、實際查證結果是什麼。沒查過的不能寫「安全」。｜取代「應該沒問題」
第三段 — 驗收清單寫成可勾選的：開哪一頁、看哪個面板、預期看到什麼數字，逐條列出。需要測試帳號才驗得了的，就標記為未完成。｜誰接手都能重跑
結語條：成果：導航阻塞 40ms → 26ms、banner 重複請求 18 → 4 次。但真正省下時間的不是這些數字，是下一頁。

P17 · §16 另一種驗證（推翻）
標題：查證的產出，是推翻了幾件事
引言：研發部門的審查報告列了 26 項。逐項查證之後，有幾項的結論跟報告不一樣——這些都是「照著做就會出事」的項目。
左欄｜被推翻 — 照著做會壞掉的部分
「這個套件沒用到」——它是金流套件的相依，刪了會壞
「這段輪詢可以直接刪」——結論對、理由錯：刪了會顯示錯的法遵文案
「這兩支請求該並行」——後面那支要帶前面的結果，串行是必要的
右欄｜自我檢查 — 驗證方法本身也會出錯
用 HTTP 200 確認檔案還在不在，看起來一切正常
加一個對照組：拿一個不存在的檔名去要——回應一模一樣
代表這個方法沒有鑑別力。方法要先自證有效，結果才算數
結語條：驗證不只是確認做對了，更多時候是問出「這件事到底該不該做」。細節整理成一份可逐項點開的網頁，等一下直接看。

P18 · §17 支撐（文件）
標題：四道關卡的做法，寫成專案內的文件
引言：四道關卡有三道由人執行。為了讓執行方式一致，做法統一寫成文件放在專案裡。
圖說：後端專案的開發規範文件（節錄）。前端另有一份對應的規範。
右欄四點
每一道關卡都寫成文字：什麼時候做、怎麼做、做到什麼程度才算通過。
新功能先寫檢查、修問題先寫重現：順序固定下來，不用每次重新討論。
檢查放哪裡、怎麼跑，都是固定的：找得到程式，就找得到對應的檢查。
成員與 AI 開發工具讀同一份：AI 接手時依據一樣，不需要另外口頭交代。
結語條：這份文件同時供成員與 AI 開發工具讀取，兩者依據相同。

P19 · §18 影響（對聽眾）
標題：這對各位的實際差別
三欄
提需求的時候 — 我們會問得更多、更早：在還沒開始寫之前，我們會把不清楚的地方先問完。來回的次數不會變少，但會集中在最便宜的階段。
回報問題的時候 — 問題修好後會留下一條檢查：同一個問題如果之後又被改壞，那條檢查會立刻亮紅燈。修過的東西不容易重覆發生。
上線的時候 — 沒全過就送不進共用版本：這道關卡是自動的，不靠人記得要做。程式要被部署出去之前，一定跑過這一關。
結語條：需要說明的是：這些關卡降低「改動波及其他功能」的機率，並讓問題盡量在上線前出現，但不保證零錯誤。畫面與操作情境目前仍以人工確認為主，正在用 Claude in Chrome 的 E2E 補上。

P20 · §19 總結（表格）
標題：什麼時候，用哪一個
引言：不是每次改動都要全套走完。以下是實務上的取用方式。
工具	什麼時候用	怎麼執行	強制程度
/grill-me	大需求、規格模糊	動手寫程式之前叫一次，追問到答得出來	靠紀律
TDD 先寫檢查	新需求、新規則、修 bug	人先寫下驗收條件，AI 再照著寫實作	寫進規範
/pre-commit-review	每一次提交之前	commit 前叫一次，或掛 hook 自動攔	hook 強制
自動測試 189 條	每一次推送	推送前全部重跑，沒過就送不出去	機器強制
E2E · Claude in Chrome	畫面與操作流程	前端改動後，開真的瀏覽器走一遍	試作中
前後對照 ＋ 影響清單	效能、重構、刪碼	先量基準線，再逐項查證波及範圍	靠紀律
結語條：一句話的原則：需求越大越模糊，越值得先問；會被重複驗證的規則，交給檢查；每次都該做的事，掛上 hook 讓它自己發生。
